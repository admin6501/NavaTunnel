# نگهداری NavaTunnel

[English](OPERATIONS.md) · [صفحه اصلی](../README.fa.md) · [راهنمای تونل](USAGE.fa.md) · [دستورها](CLI.fa.md) · [پرسش‌ها](FAQ.fa.md)

دستورها را با root اجرا کن و قبل از اجرا، مقدارهای نمونه با حروف بزرگ و `ID` را با مشخصات واقعی جایگزین کن.

## ترافیک و سقف

از منوی اصلی **۶** یا گزینه **۹** مدیریت تونل روی ایران استفاده کن. مشخص کن دانلود، آپلود یا هر دو برای سقف حساب شوند. با رسیدن به سقف، ترافیک همان شمارنده مسدود می‌شود. ریست مصرف، مسدودی سقف را هم رفع می‌کند. سقف صفر یعنی نامحدود.

```bash
NavaTunnel traffic list
NavaTunnel traffic status ID
NavaTunnel traffic limit ID 100GB --mode download
NavaTunnel traffic mode ID both
NavaTunnel traffic reset ID
NavaTunnel traffic limit ID 0
```

تنها واحد ورودی و نمایش، GB ده‌دهی است؛ هر GB یک میلیارد بایت است. ورودی `100` و `100GB` هر دو یعنی ۱۰۰ GB؛ واحدهای GiB، MB و مانند آن پذیرفته نمی‌شوند. دانلود یعنی دریافت توسط سروری که شمارنده روی آن اجرا می‌شود و آپلود یعنی ارسال آن. تغییر نحوه محاسبه، همان آمار قبلی را با روش جدید حساب می‌کند و دوره تازه‌ای نمی‌سازد. ریست، مصرف را صفر می‌کند ولی سقف و نحوه محاسبه را نگه می‌دارد. شناسه شمارنده در `traffic list` مشخص است و با شناسه تونل ایران یا اتصال خارج یکی نیست.

شمارنده عادی GRE ترافیک IPv4 داخل تونل را اندازه می‌گیرد؛ دیتاسنتر ممکن است سربار، ارسال مجدد و ترافیک‌های دیگر را هم حساب کند. شمارنده بر اساس IP مقابل، همه ترافیک IPv4 بین دو IP را حساب می‌کند، حتی اگر متعلق به برنامه دیگری باشد. شمارنده‌های هم‌پوشان نساز. دو طرف از دید متفاوتی شمارش می‌کنند؛ مجموع مصرف ایران و خارج، مصرف قابل‌صورتحساب یک دیتاسنتر نیست.

پایش هر ۱۰ ثانیه انجام می‌شود. برای تعمیر پایش بدون ریست آمار و سقف‌ها:

```bash
NavaTunnel traffic repair
systemctl status NavaTunnel-traffic.timer --no-pager
journalctl -u NavaTunnel-traffic.service -n 50 --no-pager
```

## تنظیمات شبکه و امنیت

گزینه‌های منوی اصلی **۲**:

- **۱:** بهینه‌سازی شبکه، BBR، بافر TCP و MTU.
- **۲:** GRE مستقیم، FOU و رفتن به روش انتقال بعدی.
- **۳:** محدودیت نرخ SYN پورت‌های سرویس. این محدودیت روی اتصال‌های جدید اثر می‌گذارد؛ عدد بیش از حد پایین می‌تواند به کاربران آسیب بزند. این گزینه تضمین مقابله با DPI یا فیلترینگ نیست.
- **۴:** ترافیک پوششی تصادفی ICMP. بسته اضافی می‌فرستد و مصرف دارد؛ حجم یک تونل پُرمصرف را مخفی نمی‌کند.
- **۵:** واچ‌داگ، زمان‌بندی بکاپ و هشدار اختیاری تلگرام. قبل از فعال‌کردن هشدار، توکن و مقصد را خودت تنظیم کن. روشن‌کردن پایش به‌تنهایی ری‌استارت خودکار را فعال نمی‌کند؛ مقدار اولیه `auto_restart` خاموش است.
- **۶:** تنظیمات و وضعیت رمزگذاری، فشرده‌سازی و TLS در FRP.
- **۷:** نگهداری حافظه و swap.
- **۸:** بازگرداندن تنظیمات ذخیره‌شده شبکه.

GRE و FOU به‌تنهایی رمزگذاری ندارند. FRP نسخه ۰٫۷۱ به‌صورت پیش‌فرض TLS دارد، ولی رمزگذاری با تأیید هویت گواهی یکسان نیست. تنظیمات واقعی FRPC/FRPS را بررسی کن و در صورت نیاز از TLS برنامه استفاده کن. اسکریپت برای اینباند برنامه گواهی صادر نمی‌کند. جبران افت KCP/FEC و ترافیک پوششی می‌توانند مصرف دیتاسنتر را افزایش دهند.

این ابزارها در سطح همین سرور هستند. دستورهای کلی روش انتقال ممکن است همه رابط‌های فعال GRE را تغییر بدهند؛ برای یک مسیر، گزینه روش انتقال همان تونل را استفاده کن. رفتن به روش بعدی، انتخاب خودکار بین ایران‌ها نیست و پکت‌لاس اینترنت کاربران را اندازه نمی‌گیرد.

### سفارشی‌کردن ترافیک پوششی و محدودیت SYN

روی سروری که می‌خواهی ترافیک پوششی داشته باشد، از **۲ ← ۴ ← ۶** فاصله و اندازه بسته‌ها را ذخیره کن و با **گزینه ۷** حالت سفارشی را فعال کن. پینگ‌های پوششی حتی هنگام ترافیک کاربران ادامه دارند. معادل خط فرمان:

```bash
NavaTunnel chaff configure --min-ms 400 --max-ms 2800 --min-bytes 64 --max-bytes 1200
NavaTunnel perf chaff custom
NavaTunnel chaff status
```

برای خاموش‌کردن، `NavaTunnel chaff off` را اجرا کن. فاصله‌ها بر حسب میلی‌ثانیه و اندازه داده بر حسب بایت است و باید در MTU جا شود. این تنظیم برای ترافیک پوششی مدیریت‌شده همین سرور است، نه فقط یک تونل انتخاب‌شده.

روی ایران، از **۲ ← ۳ ← ۴** نرخ و burst را تنظیم کن و با **گزینه ۱** قواعد را فعال کن. اعداد زیر نمونه‌اند، نه مقدار مناسب قطعی برای همه:

```bash
NavaTunnel dpi-shield configure --rate 60/sec --burst 120
NavaTunnel dpi-shield on
NavaTunnel dpi-shield status
```

برای خاموش‌کردن، `NavaTunnel dpi-shield off` را اجرا کن. محدودیت برای بسته‌های TCP SYN به تفکیک IP مبدأ و پورت سرویس است؛ تعداد درخواست برنامه در دقیقه یا سرعت دانلود را تعیین نمی‌کند. کاربران پشت یک NAT ممکن است IP مشترک داشته باشند. این قابلیت ترافیک پوششی نمی‌سازد. انتخاب‌های `perf enc` و `comp` و `tls` به اجرای `NavaTunnel perf apply` نیاز دارند؛ این دستور روی تنظیمات و سرویس‌های همین سرور اعمال می‌شود، نه فقط یک اتصال انتخاب‌شده. دو طرف را هماهنگ کن.

### نیازهای فایروال و دیتاسنتر

| ترافیک | مسیر لازم |
| --- | --- |
| پورت SSH انتخاب‌شده | مبدا مدیریت یا انتقال به مقصد |
| پورت‌های سرویس TCP/UDP | کاربران به ایران؛ پورت محلی برنامه متناظر روی خارج |
| GRE مستقیم، پروتکل IP شماره **۴۷** | بین IP عمومی دو سرور؛ منظور پورت TCP/UDP شماره ۴۷ نیست |
| پورت UDP مربوط به FOU، معمولاً ۴۴۳ یا ۵۵۵۵۵ | بین IP عمومی دو سرور، وقتی این روش فعال است |
| ارتباط کنترل FRP | خارج به آدرس GRE ایران؛ TCP برای TCP/WS/WSS و UDP برای KCP/QUIC |

هم فایروال سیستم‌عامل و هم فایروال دیتاسنتر را بررسی کن. در صورت امکان دسترسی بین دو سرور را به همان IPها محدود کن. برای بررسی یک پورت، کل فایروال را خاموش نکن. داشتن root داخل کانتینر لزوماً مجوز شبکه و کرنل لازم برای GRE/FOU را فراهم نمی‌کند.

## بکاپ

از **۳ ← ۵** استفاده کن یا اجرا کن:

```bash
NavaTunnel backup now
NavaTunnel backup status
```

فایل رمزگذاری‌شده در `/var/backups/navatunnel/` با نامی مانند `navatunnel-backup-YYYYMMDD-HHMMSS.enc` ذخیره می‌شود. کلید آن `/etc/gre-panel/backup.key` است. فایل بکاپ و کلید اصلی آن را با هم نگه دار؛ کلید جدید، بکاپ قدیمی را باز نمی‌کند. پیش‌فرض هفت بکاپ باقی می‌ماند؛ گزینه `backup now --keep N` تعداد نگهداری همان اجرا را تغییر می‌دهد.

بکاپ شامل تنظیمات مدیریت‌شده، توکن‌ها، شمارنده‌ها و سرویس‌هاست؛ دیتابیس و کاربران برنامه روی خارج یا فایل اجرایی FRP را شامل نمی‌شود. برای برنامه خودت جداگانه بکاپ بگیر. هسته FRP هنگام ریستور نصب می‌شود.

پوشه‌هایی مثل `TIMESTAMP_pre_setup_foreign` و `iran-ip-*` و `gre-addresses-*` نسخه ایمنی محلی تغییرات‌اند و فایل رمزگذاری‌شده قابل‌ورود به `backup restore` نیستند. بکاپ تازه انتقال SSH ممکن است داخل زیرپوشه `migration-*` باشد؛ مسیر چاپ‌شده را استفاده کن. دستور `backup status` فقط فایل‌های `.enc` سطح اول پوشه بکاپ را نشان می‌دهد.

### زمان‌بندی بکاپ

از **۳ ← ۷** زمان‌بندی ساعتی یا روزانه را ذخیره کن. معادل خط فرمان، یکی از این دو:

```bash
NavaTunnel backup schedule --every 6
```

```bash
NavaTunnel backup schedule --daily 03:00
```

ذخیره زمان‌بندی کافی نیست؛ تایمر نگهداری هم باید نصب و فعال باشد. دستور `NavaTunnel watchdog on` تایمر را همراه پایش فعال می‌کند. با `systemctl status navatunnel-watchdog.timer --no-pager` و `NavaTunnel watchdog status` وضعیت را ببین. ساعت روزانه بر اساس ساعت محلی سرور است؛ با `timedatectl` بررسی کن. دستور `NavaTunnel backup schedule --off` زمان‌بندی را لغو می‌کند. دستور `watchdog off` هشدارهای پایش را غیرفعال می‌کند ولی تایمر نگهداری را باقی می‌گذارد و زمان‌بندی ذخیره‌شده را لغو نمی‌کند. بکاپ‌ها را خارج از همان سرور هم نگه دار.

## ریستور

اول NavaTunnel را روی مقصد نصب کن. بکاپ و کلید اصلی را امن منتقل کن و کلید اصلی را قبل از ریستور در `/etc/gre-panel/backup.key` قرار بده. اگر بکاپ‌های قبلی مقصد را لازم داری، کلید قبلی مقصد را هم جدا نگه دار.

بررسی بکاپ بدون اعمال تغییر:

```bash
NavaTunnel backup restore /var/backups/navatunnel/BACKUP.enc --dry-run
```

ریستور با همان IP:

```bash
NavaTunnel backup restore /var/backups/navatunnel/BACKUP.enc
```

ریستور روی سرور جایگزین **ایران یا خارج** با IP جدیدی که از قبل روی سرور تنظیم شده:

```bash
NavaTunnel backup restore /var/backups/navatunnel/BACKUP.enc --local-ip DESTINATION_PUBLIC_IP
```

گزینه `--local-ip` همیشه یعنی **IP عمومی خود سرور جایگزین**؛ فرقی ندارد ایران باشد یا خارج. آدرس محلی GRE و IP محلی فهرست تونل‌ها را اصلاح می‌کند؛ IP مقابل، توکن‌ها و سقف‌ها حفظ می‌شوند. بدون این گزینه، آدرس محلی قبلی باقی می‌ماند. ریستور منوی **۳ ← ۶**، IP جدید نمی‌پرسد؛ اگر IP مقصد متفاوت است از همین دستور خط فرمان استفاده کن.

ریستور از تنظیمات قبلی نسخه خصوصی می‌گیرد، مسیرهای آرشیو را اعتبارسنجی می‌کند، FRP را نصب می‌کند، فایل‌ها را برمی‌گرداند و پایش ترافیک را تعمیر می‌کند. توقف دستی قبلی تونل‌ها حفظ می‌شود. اگر سرویسی بالا نیامد، خطا را بررسی کن؛ استخراج فایل به‌تنهایی نشانه برقراری ارتباط نیست. بعد از تغییر آدرس، مراحل مربوط به نقش سرور را در ادامه انجام بده.

### انتقال دستی بکاپ و کلید

روی مبدا، `DESTINATION_IP` و نام نمونه بکاپ را جایگزین کن:

```bash
ssh root@DESTINATION_IP 'install -d -m 700 /root/navatunnel-transfer'
scp /etc/gre-panel/backup.key /var/backups/navatunnel/BACKUP.enc root@DESTINATION_IP:/root/navatunnel-transfer/
```

روی مقصد NavaTunnel را نصب کن. اگر بکاپ‌های قبلی مقصد را لازم داری، اول کلید قبلی‌اش را جدا نگه دار. سپس روی مقصد کلید مبدا را نصب و بکاپ را بررسی کن:

```bash
install -d -m 700 /etc/gre-panel
install -m 600 /root/navatunnel-transfer/backup.key /etc/gre-panel/backup.key
chmod 600 /root/navatunnel-transfer/BACKUP.enc
NavaTunnel backup restore /root/navatunnel-transfer/BACKUP.enc --dry-run
```

بعد همان مسیر را ریستور کن؛ به‌جای `DESTINATION_PUBLIC_IP`، IP عمومی خود مقصد را بنویس:

```bash
NavaTunnel backup restore /root/navatunnel-transfer/BACKUP.enc --local-ip DESTINATION_PUBLIC_IP
```

برای پورت SSH غیرپیش‌فرض، گزینه `ssh` برابر `-p PORT` و گزینه `scp` برابر `-P PORT` است.

## انتقال با SSH

منوی **۳ ← ۸ را روی سرور قدیمی یا مبدا** اجرا کن. هم برای ایران و هم برای خارج کار می‌کند؛ خارجِ متصل به چند ایران هم پشتیبانی می‌شود. تنظیمات مدیریت‌شده کل همین سرور منتقل می‌شود، نه فقط تونلی که در منوی دیگری انتخاب کرده بودی.

| پرسش منو | چه چیزی وارد کنی |
| --- | --- |
| Destination IPv4 | IP سرور جدید برای اتصال SSH |
| SSH port | پورت SSH مقصد؛ Enter یعنی ۲۲ |
| SSH user | کاربر root یا کاربر دارای sudo بدون رمز |
| SSH private key path | مسیر **فایل کلید** موجود، یا Enter برای رمز/agent؛ اینجا رمز ننویس |
| Existing encrypted backup path | مسیر فایل `.enc` موجود روی مبدا همراه کلید اصلی‌اش؛ Enter یعنی ساخت بکاپ تازه |
| Destination tunnel public IPv4 | **IP عمومی خود سرور جدید**؛ Enter یعنی همان IP مقصد SSH |

فیلد آخر هنگام انتقال خارج یعنی **IP خارج جدید** و هنگام انتقال ایران یعنی **IP ایران جدید**؛ منظور IP طرف مقابل نیست. اگر مقصد در ورود اول تغییر اجباری رمز دارد، ابتدا با ورود تعاملی مثل `ssh -t root@DESTINATION_IP` رمز را عوض کن.

مقصد باید systemd، اینترنت برای دانلود وابستگی‌ها و دسترسی root یا کاربر دارای sudo بدون رمز داشته باشد. تنظیمات مقصد پس از تهیه نسخه خصوصی جایگزین می‌شوند. مبدا روشن می‌ماند.

```bash
NavaTunnel migrate --host DESTINATION_IP --local-ip DESTINATION_PUBLIC_IP
```

گزینه‌های اختیاری: `--port 2222`، `--user ubuntu`، `--identity /root/.ssh/id_ed25519` و `--backup /path/to/BACKUP.enc`.

### بعد از انتقال ایران

1. روی ایران مقصد از **۱ ← ۴** فهرست تونل‌ها را ببین و مطمئن شو IP ذخیره‌شده ایران، IP جدید است.
2. انتقال، مسیر فایلی شبیه `/var/backups/navatunnel/migration-*-foreign-commands.txt` را روی مقصد چاپ می‌کند. این فایل دستورهای محرمانه جدید را دارد. از **۱ ← ۳ ← انتخاب تونل ← ۸** هم می‌توانی کد هر تونل را بگیری.
3. روی هر خارج مربوط، اتصال قبلی همان ایران را انتخاب کن؛ با **گزینه ۹** IP ایران را عوض کن یا با **گزینه ۶** کد جدید را اعمال کن. در جایگزینی خط فرمان حتماً `--foreign-id N --force` با شناسه درست بده؛ این نکته برای دستورهای فایل تولیدشده روی خارج چنداتصاله هم لازم است.
4. در صورت نیاز آدرس کاربران یا DNS را اصلاح کن، برنامه را روی همه مسیرها تست کن و بعد ایران قدیمی را بازنشسته کن.

### بعد از انتقال خارج

1. روی خارج مقصد، `NavaTunnel foreign-list` را اجرا کن؛ همه اتصال‌های ایران باید در فهرست باشند.
2. برنامه را جدا منتقل کن: Xray/V2Ray یا پنل، اینباندها، کاربران، دیتابیس و گواهی‌های موردنیاز. بکاپ NavaTunnel آن‌ها را منتقل نمی‌کند.
3. روی **هر ایران متصل** از **۱ ← ۳** تونل مربوط را انتخاب کن و با **گزینه ۶، Change foreign server IP**، IP خارج جدید را وارد کن. IP عمومی خود ایران تغییر نکرده است.
4. از مسیر هر ایران برنامه را تست کن. اگر تنظیمات ریستورشده خارج نیاز به اصلاح داشت، همان اتصال را انتخاب و به‌روز کن و اتصال تکراری نساز. فقط بعد از تأیید همه مسیرها خارج قدیمی را بازنشسته کن.

پیام موفقیت انتقال یعنی نصب و ریستور تنظیمات انجام شده؛ سرورهای مقابل، دیتابیس برنامه و اشتراک‌ها خودکار تغییر نمی‌کنند. مبدا متوقف نمی‌شود. آرشیو قبلی مقصد، نسخه ایمنی خصوصی است و به معنی برگشت خودکار تمام مراحل ناموفق نیست.

## عیب‌یابی

از **۳ ← ۱** یا دستور `NavaTunnel status` شروع کن. لاگ‌ها در **۳ ← ۳** یا `NavaTunnel logs` در دسترس‌اند.

```bash
systemctl status frps frpc --no-pager -l
journalctl -u frpc -n 50 --no-pager
```

روی ایران چندتونله، نام سرویس همان تونل را بررسی کن؛ مثلاً ممکن است سرویس آن `frps-2` باشد. برای دیدن تنظیمات رابط اول:

```bash
ip -d tunnel show gre-tunnel
ip -4 addr show dev gre-tunnel
```

برای بررسی سلامت با آدرس واقعی همه اتصال‌ها از **۳ ← ۱** یا `NavaTunnel doctor check` استفاده کن. دستور `status` وضعیت سرویس را هم نشان می‌دهد، ولی پینگ قدیمی رابط اول جای انتخاب آدرس واقعی مقابل را نمی‌گیرد. آدرس داخلی مقابل را از تنظیمات بگیر؛ همیشه `10.10.10.1` یا `10.200.0.1` نیست و تخصیص جدید منو می‌تواند در محدوده `10.64.0.0/10` باشد. پینگ IP عمومی دقیقاً مسیر ترافیک برنامه را آزمایش نمی‌کند. افت ICMP می‌تواند ناشی از فیلتر یا محدودیت نرخ هم باشد.

برای رابط انتخابی، هر دو مقدار نمونه را جایگزین کن:

```bash
ping -n -I GRE_INTERFACE -c 100 -i 0.2 -W 2 -w 30 PEER_GRE_IP
```

برای تست طولانی‌تر که با قطع SSH ادامه پیدا کند:

```bash
nohup ping -n -I GRE_INTERFACE -c 1000 -i 0.2 -W 2 -w 240 PEER_GRE_IP > /tmp/navatunnel-ping.log 2>&1 < /dev/null &
```

بعد با `tail -n 5 /tmp/navatunnel-ping.log` نتیجه را ببین. برای بسته نزدیک MTU، گزینه `-M do -s PAYLOAD_BYTES` را اضافه کن؛ در ICMP روی IPv4، اندازه داده نباید از MTU داخلی منهای ۲۸ بیشتر باشد. مشخص کن تست هنگام مصرف کاربران بوده یا بیکاری. مقدار `mdev` نوسان RTT است و لزوماً همان تعریف جیتر هر برنامه نیست. پینگ سالم در بیکاری، سلامت برنامه زیر بار را تضمین نمی‌کند.

خطای `203/EXEC` معمولاً یعنی فایل اجرایی سرویس وجود ندارد یا قابل اجرا نیست. با `NavaTunnel download-cores` نصب FRP را تعمیر کن، لاگ را بررسی کن و سرویس مربوط را ری‌استارت کن. خطای TCP با متن `connection refused` یعنی مقصد اتصال را رد کرده؛ قبل از عوض‌کردن پروتکل، سرویس FRPS و پورت کنترل همان تونل را بررسی کن.

پیام `work connection pool is full, discarding` به‌تنهایی ثابت نمی‌کند پردازش ری‌استارت شده یا افت بسته وجود دارد. لاگ هر دو طرف را در زمان یکسان بررسی کن و با نام واقعی سرویس، `systemctl show FRPC_SERVICE -p NRestarts -p ActiveEnterTimestamp` را ببین. مقدار `NRestarts=0` فقط شمارنده ری‌استارت systemd است؛ اتصال مجدد FRP داخل همان پردازش را حساب نمی‌کند. فقط به خاطر این پیام، اندازه pool یا پروتکل را تغییر نده.

## محل فایل‌ها و حذف

| مسیر | محتوا |
| --- | --- |
| `/etc/frp/frps*.toml` | تنظیمات FRPS ایران و توکن‌ها |
| `/etc/frp/frpc*.toml` | تنظیمات FRPC خارج و توکن‌ها |
| `/etc/gre-panel/peers.json` | فهرست تونل‌های ایران |
| `/etc/gre-panel/foreign.json` | فهرست اتصال‌های خارج |
| `/etc/gre-panel/traffic.json` | مصرف ذخیره‌شده، روش محاسبه و سقف‌ها |
| `/etc/gre-panel/mtu.json` و `stopped/` | MTU دائمی و توقف‌های دستی |
| `/etc/gre-panel/perf.json` و `watchdog.json` | تنظیمات سرور و اطلاعات اختیاری هشدار |
| `/etc/systemd/system/gre-t*.service` | تنظیمات دائمی دو سر GRE |
| `/var/backups/navatunnel/` | بکاپ‌های رمزگذاری‌شده و نسخه‌های ایمنی خصوصی |

فایل‌های تنظیمات خصوصی‌اند؛ توکن کامل، کد اتصال، کلید بکاپ و اطلاعات تلگرام را در تیکت عمومی منتشر نکن. به‌جای ویرایش دستی فایل فعال، از منو یا CLI استفاده کن. نام پوشه `gre-panel` برای سازگاری حفظ شده و به معنی نصب پنل وب نیست.

برای حذف **یک تونل** از منوی همان تونل استفاده کن؛ روی ایران **۱۴** و روی خارج **۱۰**. منوی اصلی **۵** و دستور `remove-tunnel` روی همه تونل‌های محلی عمل می‌کنند؛ حذف کامل `uninstall`، خود NavaTunnel و پوشه `/etc/gre-panel` شامل کلید بکاپ را هم حذف می‌کند. **قبل از حذف نصب، بکاپ لازم و کلید آن را بیرون از همان سرور نگه دار.** حذف یک سر تونل، سر مقابل یا برنامه را حذف نمی‌کند.

## ارتقا از نسخه‌های قدیمی

```bash
NavaTunnel update-all
NavaTunnel
```

در نسخه ۱٫۲٫۰، کلاستر و NavaLink حذف شده‌اند. منوها، ساخت اتصال، سرویس مرکزی، APIها و کد مسیریابی آن‌ها دیگر ارائه نمی‌شود. تونل‌های معمولی GRE/FRP باقی می‌مانند.

هنگام اجرا، سرویس‌های متعلق به قابلیت‌های حذف‌شده متوقف و فقط قواعد فایروال خودشان پاک می‌شوند. تنظیمات آن‌ها در `/var/backups/navatunnel/removed-features-*` خصوصی بایگانی می‌شود. تنظیمات ابزارهای حذف‌شده قبلی ممکن است زیر `removed-tools-*` بایگانی شوند. قواعد نامرتبط فایروال، کلیدهای root و تنظیمات تونل‌های معمولی حفظ می‌شوند.

اگر NavaLink از تبدیل GRE ساخته شده باشد، فایل‌های قبلی GRE/FRP برمی‌گردند و شمارنده با حفظ مصرف و سقف دوباره به GRE متصل می‌شود. برای تکمیل برگشت، **هر دو طرف را آپدیت کن**؛ توقف دستی قبلی حفظ می‌شود. اتصال NavaLink تازه، GRE قبلی ندارد: متوقف و تنظیمات و مصرف آن بایگانی می‌شود؛ در صورت نیاز باید تونل عادی جدید بسازی. وجود تداخل یا فایل ناقص، خطای روشن می‌دهد و تونل موجود بازنویسی نمی‌شود. بکاپ قدیمی هم هنگام ریستور با همین روش پاک‌سازی می‌شود.

تنها فایل اجرایی اختیاری Go باقی‌مانده، واسط کوچک TLS برای WSS خودِ FRP است؛ کلاستر، موتور SSH، وب‌پنل یا API مدیریتی ندارد. فقط وقتی واسط WSS تنظیم شده باشد، با بررسی checksum دانلود می‌شود. نصب معمولی TCP به آن نیاز ندارد.

## بکاپ و پایش چند اتصال خارج

بکاپ شامل فهرست `foreign.json`، تنظیمات FRPC و GRE هر اتصال، روش انتقال، شمارنده‌ها و توقف‌های دستی است. ریستور همه کلاینت‌ها را با رابط درست خودشان برمی‌گرداند. پس از انتقال خارج به IP جدید، IP خارج را در تونل مربوط روی **هر ایران** اصلاح کن.

واچ‌داگ اتصال‌های ثبت‌شده خارج را جدا بررسی می‌کند؛ در صورت فعال‌بودن ری‌استارت خودکار، فقط همان اتصال خراب را ری‌استارت می‌کند. توقف دستی حفظ می‌شود. این بررسی، سلامت کلی ارتباط است و درصد دقیق افت بسته را اندازه نمی‌گیرد.
